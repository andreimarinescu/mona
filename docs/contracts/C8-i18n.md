## 1. Catalogs and the source-of-truth flow

### 1.1 Two catalogs
| Catalog | Files | Holds | Read by |
|---|---|---|---|
| web | `apps/web/src/i18n/{en,fr,ro}.json` (exists, W0) | every string the web renders | react-i18next |
| server | `apps/api/src/mona/i18n/{en,fr,ro}.json` (new) | strings the server renders into DTOs: `review.sentence.*` (C5 §9.4), `interview.option.ask` (C6 §4.5), `export.csv.*` (L4's CSV headers) | `mona.i18n.t(key, lang, **values)` |

- A key lives in exactly one catalog. Both use nested JSON objects keyed by the dotted segments, i18next interpolation `{{name}}` (C5 writes `{name}` as notation; the catalogs spell it `{{name}}`) and i18next plural suffixes (§2.3).
- The server formatter is a small function with i18next's semantics for `{{name}}`, `count` plurals (Python's CLDR plural rules for the three languages, §2.3) and context suffixes (§2.4). It never HTML-escapes (the web renders text nodes).

### 1.2 Flow
1. A lane adds a key to `en.json` (the source) with its final English text, and adds `fr` and `ro` values in the same commit. A lane that can't write a language puts in the value drafted with the glossary (an LLM draft is acceptable, R50) and lists the key in its report under "translations to review". No commit leaves a key missing in any language; CI enforces it (§10).
2. English text follows `voice-and-tone.md`: sentence case, no exclamation marks, no emoji, none of the words Mona doesn't use. French and Romanian follow its register (formal *vous*, *dumneavoastră*; buttons: FR infinitive, RO formal imperative) and its typography (§6.3).
3. A text change in `en` that changes the meaning updates `fr` and `ro` in the same commit.
4. Keys are never renamed silently: a rename removes the old key everywhere and adds the new one, in one commit.

### 2.3 Plurals
Plural keys carry i18next's CLDR suffixes and are called with `count`. Each language has exactly its CLDR categories:

| Language | Suffixes | Examples |
|---|---|---|
| en | `_one`, `_other` | 1 document · 2 documents |
| fr | `_one`, `_many`, `_other` | 1 document · 2 documents; `_one` covers 0 and 1, so its value always writes `{{count}}`, never "1" or "un"; `_many` (1 000 000 and multiples) copies `_other` |
| ro | `_one`, `_few`, `_other` | 1 document · 2–19 documente · 20 de documente (`_few` covers 0, 2–19 and n01–n19; `_other` takes "de") |

A plural key in `en` makes the check demand the full suffix set in each other language, and it accepts `fr` and `ro` suffixes that `en` doesn't have (§10). `_zero` is not used; a zero case is its own key (`home.brief.filedNone`).

### 2.4 Context variants
A key may have i18next context variants `<key>_<context>` for a grammatical alternative the placeholder can't express. The only context this contract defines is `_anon`: on `review.sentence.*` (no counterparty, §5.4) and on `home.brief.greeting.*` (no form of address, §5.6).

## 3. Languages at run time

### 3.1 Interface language
- The interface language is `profile.locale` (C1 §8), chosen in `FirstRunChecklist` and changed in Settings, nowhere else (HANDOFF §4). The browser's language is never consulted.
- The web reads it from `GET /api/auth/state` (so `/unlock` renders in it too, C2 §2.5), sets i18next's language, `<html lang>`, and passes it to every `Mona.format` call. A Settings change switches all three at once.
- Server-rendered strings use the **request locale**, which is `profile.locale` at request time (C2 §1.1 item 5). Chat cards use it too (C3 §5.5).

### 3.2 Conversation language
- The web sends `locale` = the interface language on every chat turn (C3 §2).
- The reply language is C3 §4.2's order: the request's `replyLanguage` ("Keep English"), then `detect_language(message)` (§4), then the previous turn's, then `locale`.
- The interface doesn't change with the conversation: a French question in an English interface gets a French answer, an English interface, and a `LanguageDivider` (C3 §3.4).
- Accessibility: an assistant message whose `replyLanguage` differs from the interface language carries `lang="<replyLanguage>"` on its text container (HANDOFF §5).

| Content | Language |
|---|---|
| Folder names, `{category}`/`{sub}` tokens, model titles | the filing language: `entity.filing_language ?? settings.filing_language` (C5 §8.2), default `fr`; never the interface language |

| Evidence quotes, document titles and extracted values | as printed, never translated |

## 4. `detect_language`

`mona.i18n.detect_language(text: str) -> 'en' | 'fr' | 'ro' | None`, used by the chat adapter (C3 §4.2). It replaces C3's interim rule (C3 §9 item 4) and fixes its known miss: Romanian written without diacritics ("Cat am platit la AGIPI anul trecut?" tied French and Romanian).

### 4.1 Algorithm
1. `s = unicodedata.normalize('NFC', text)`. Words are the maximal runs of Unicode letters (`[^\W\d_]+`); apostrophes (`'`, `’`) and hyphens split words ("l'échéance" → `l`, `échéance`).
2. **Letter cues**, on the lower-cased **cue words**: the first word, and every later word that doesn't start with an upper-case letter. A capitalised word inside the text is usually a name (a folder, a counterparty, a label), and French folder names carry accents (R17). The RO cue is any of `ă ș ş ț ţ`; the FR cue is any of `é è ê ë à ç ù û ô œ ï ÿ`. (`â` and `î` are shared and give no cue.) Each cue counts once, worth **1** for its language: a tie-breaker, so accents can't outweigh a sentence's words.
3. **Word hits.** For each word of 2 or more letters, `w = norm(word)` (C5 §2, so diacritics fold on the input as they already are in the lists). A `w` scores **1** for every list (§4.2) it appears in.
4. Words counted: all words of 2 or more letters. If fewer than 3 such words, return the cue language when exactly one cue is present, else `None`.
5. Otherwise return the language with the highest score if that score is at least 2 and at least 1 above the runner-up; else `None`.

Proper nouns (AGIPI, URSSAF) score nothing because they're in no list.

## 6. Formatting

### 6.1 One formatter
Every number, amount, percentage, date, time, relative time and file size the web shows goes through `Mona.format` (DS `formatting.md`) with the interface language. The server never pre-formats numbers or dates for the web: DTOs carry `Money {value, currency}`, ISO dates and timestamps, and confidence 0–100 (shown as `format.percent(confidence / 100, lang)`). The one exception is `Rule.condition`, rendered on the server in three languages (§6.4).

### 6.2 Rules the design fixes
Straight from `formatting.md`, restated because tests check them:

| Call | en | fr | ro |
|---|---|---|---|
| `money(1284.6, 'EUR')` | €1,284.60 | 1 284,60 € | 1.284,60 € |
| `money(4812, 'RON')` | 4,812.00 lei | 4 812,00 lei | 4.812,00 lei |
| `percent(0.62)` | 62% | 62 % | 62% |
| `date(d)` long | 14 March 2026 | 14 mars 2026 | 14 martie 2026 |
| `date(d, 'short')` | 14/03/2026 | 14/03/2026 | 14.03.2026 |

- French spaces are U+00A0 (the brand fonts lack U+202F); `Intl` output is post-processed to replace U+202F with U+00A0.
- RON is always written "lei", never "RON".
- **Calendar dates** (`YYYY-MM-DD`: `docDate`, `dueDate`, `periodEnd`) are parsed as local calendar dates (`new Date(y, m - 1, d)`), never with `new Date('YYYY-MM-DD')`, which is UTC midnight and shows the previous day west of UTC. Timestamps (ISO with `Z`) are shown in the browser's time zone; the practice's machines run Europe/Paris (the stage laptop Europe/Rome, the same offset).

### 6.3 Typography in strings
- French: U+00A0 before `; : ? !` and `%`, inside « » (`« {{question}} »`), and between a number and its unit in catalog strings.
- Romanian: quotes „…” (U+201E … U+201D); comma-below letters (§7).
- English: “…” for quotations; `…` (U+2026) for ellipses in every language.

### 6.4 Server-side formatting
Only generated documents format on the server: drafted replies (L4's `.docx`: dates in the letter's language) and, if L4 localises them, CSV values. They use `mona.i18n.format_date(d, lang)` and `format_money(value, currency, lang)`, which reproduce §6.2's long-date and money rows exactly (tested with the same vectors). Card-action notes and MCP results stay English with ISO dates (C3 §6.2, C4 §2.1).

`condition_text` (C5 §4.7, served as `Rule.condition`) renders amounts on the server too: `{money}`, `{a}` and `{b}` are the number part of `format_money`, with §6.2's grouping and decimal marks, two decimals and no currency (a rule's amount has none). French groups thousands with U+00A0 (`1 284,60`), Romanian with `.` (`1.284,60`), English with `,`. F0's renderer (`mona/rules/text.py`) uses a plain space for French today; §8 carries the fix into amendment A7.

## 7. ș and ț

C5 §2's `norm()` is the only normaliser: it folds ș/ş to s and ț/ţ to t (with every other diacritic), and search, rules, counterparty resolution, evidence verification, conversation-title search and `detect_language`'s word hits all go through it. This section doesn't redefine it; it covers what `norm()` doesn't: the text people read.

1. **Strings we write** in Romanian use comma-below: ș U+0219, ț U+021B, Ș U+0218, Ț U+021A. Never the cedilla forms ş U+015F, ţ U+0163, Ş U+015E, Ţ U+0162. This covers `ro.json` in both catalogs, `labels.ro` in the seed (`demo/seed/practice.yaml`), and any Romanian text in the repo's product copy. CI enforces it (§10).
2. **Text Mona generates in Romanian** goes through `mona.i18n.ro_comma_below(s)` (ş→ș, ţ→ț, Ş→Ș, Ţ→Ț) before storage: interview questions and option labels when `lang='ro'` (C6 §4.5), drafts when `lang='ro'`, and rule names built from them. Model titles stored for a Romanian filing language go through it too (amendment A6 to C5 §3/§5.2).
3. **Text from documents** (quotes, extracted values, titles as printed, file names people gave) is never rewritten: evidence must match the page (C5 §6.1, §7).
4. **Input** (search, chat, the correction picker) may use either form; `norm()` makes them equal, and `detect_language` counts both forms as the RO cue (§4.1).
5. **File names** drop both forms to s/t (C5 §8.4); **folder names** keep them as the label has them (C5 §8.3), which rule 1 makes comma-below.

## 10. The CI rule

`scripts/i18n-check.mjs` (W0) runs in `make check` and CI (D1). L3 extends it (and L2 adds the server catalog to it) so that each of these fails the build, with one line per problem:
1. A key in `en` missing from `fr` or `ro`, or a key in `fr`/`ro` that `en` lacks, per catalog, with plural keys compared by base key and each language's §2.3 suffix set (the W0 check's "has a key en lacks" error must accept `fr` `_many` and `ro` `_few`).
2. A key present in both catalogs.
3. Different placeholder sets for one key across languages. `{{count}}` may be missing only from the `_one` form of `en` and `ro`, which may spell the number; French `_one` covers 0 as well (§2.3), so it must carry `{{count}}`.
4. An empty value.
5. A cedilla letter (U+015E, U+015F, U+0162, U+0163) in any `ro.json` value, or in `labels.ro` of `demo/seed/practice.yaml`.
6. A literal key used in the web source (`t('…')`, `i18nKey="…"`) or the server source (`t("…")` in `apps/api/src/mona`) that its catalog lacks, and a key listed in `dynamic-keys.ts` that the catalog lacks.
7. Any key named in §5 missing (the check carries the list).
8. A key in §5's list or in `dynamic-keys.ts` that is also the prefix of another listed key (`a.b` and `a.b.c`): nested JSON can't hold both a string and an object at `a.b`.

Reported but not failing: a `fr`/`ro` value identical to `en` (possibly untranslated), except values in an allowlist (`Mona`, brand and product names, `OK`).
