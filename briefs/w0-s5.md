## Build

1. **Hermes in compose.**
   - Add a `hermes` service: the D3 image by digest; `gateway run`; `HERMES_UID`/`GID`; a named volume at `/opt/data`, seeded from `deploy/hermes/` (`config.yaml` + `SOUL.md`) on first start; API server env from `.env` (`HERMES_API_KEY` → `API_SERVER_KEY`); no host port except `127.0.0.1:${MONA_HERMES_PORT:-8642}` in dev.
   - Write `deploy/hermes/config.yaml` (dev) from `docs/spikes/s1/config.spike.yaml`, with the MCP URL `http://api:8765/mcp`.
   - Hermes must **not** reuse the Python services' `x-python` anchor or `env_file: .env`. Pass only the variables it needs by name. In dev that includes `OPENROUTER_API_KEY`; the prod overlay never will (D3, Egress).
   - Add `HERMES_PORT` next to the scaffold's `WEB_PORT` / `API_PORT` / `POSTGRES_PORT`. Run with `PLAYWRIGHT_SKIP_BROWSER_GC=1`.
2. **Spike MCP inside the api.**
   - Mount a FastMCP server at `/mcp` on the FastAPI app, behind the `MONA_SERVICE_KEY` bearer check.
   - Tools, synthetic data only: `search_documents`, `get_document` and `start_interview`, shaped like `spike_mcp.py`.
   - `search_documents` and `get_document` write a `card_events` entry per document (a `data-doc` card). `start_interview` writes one `data-interview` card with 1 question and 3 options.
   - Each result includes the `card_ref`s.
   - Storage can be a small table created in the spike's own Alembic migration (`spike_*` tables, dropped when C1 lands) or an in-process store. Explain the choice in the report.
3. **Adapter** (`apps/api/mona/chat/`), `POST /api/chat`: `{conversationId?, message, pageContext: {route, summary}, locale}`.
   1. Map `conversationId` → Hermes session (create one via `POST /api/sessions` if new).
   2. Open a turn lease.
   3. Call Hermes `POST /v1/chat/completions` with `stream: true`, `X-Hermes-Session-Id`, and a `system` overlay message (page context + reply-language line + pending notes).
   4. Translate to the AI SDK UI Message Stream (`x-vercel-ai-ui-message-stream: v1`):
      - `reasoning_content` → reasoning parts;
      - `content` → text parts;
      - `hermes.tool.progress` → tool parts with a readable label;
      - after each tool completes and at finish, look up the turn's `card_events` and emit `data-doc` / `data-interview` parts, each with a stable id;
      - finish.
   5. At finish, reconcile against `GET /api/sessions/{id}/messages` (tool results contain the `card_ref`s) and emit any card not yet sent.
   6. Hermes unreachable → an error part.
   - Unit-test the translator against the S1 fixture files: pure function, fixture in, parts out.
4. **Web** (`apps/web`): add `@assistant-ui/react` and `ai` / `@ai-sdk/react` (current stable; record the versions).
   - A `/dev/chat` route with the thread, composer, a `ThinkingBlock`-like reasoning display (native `<details>`, "Mona is thinking…" while live), tool activity chips, and renderers for the `data-doc` and `data-interview` parts built from the DS shim (`Card`, `Button`, `Badge`, `ConfidenceMeter`; not the final designs).
   - The page sends `pageContext` and `locale` with each turn.
5. **Measure** time to the first reasoning token and to the first text token in the browser (Playwright): cold after a Hermes restart, and warm.

## Acceptance (fresh output in the report)

- `docker compose -p mona-s5 up -d --build` brings up the whole dev stack with Hermes.
- A Playwright e2e on `/dev/chat` asks "Find the URSSAF letter" and sees:
  - a reasoning block;
  - streamed text;
  - a tool chip;
  - at least one rendered `data-doc` card.

  A second prompt, "Start an interview about AGIPI", renders an `InterviewCard` with 3 options.
- Timings table: cold and warm, first reasoning and first text; the pass line is ≤ 10 s.
- The translator unit tests pass against the S1 fixtures. Mutation check: drop the reasoning mapping and watch a test fail.
- Transcript reload: reloading `/dev/chat?c=<id>` re-renders the earlier cards.
- `make check` passes. Tear down with `docker compose -p mona-s5 down`.
